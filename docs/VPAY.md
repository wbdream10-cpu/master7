# VPay 接入与安全结算边界

依据 [Trader API Integration Documentation](https://gateway.vpay.club/api/doc/trader_en)，公开正文读取于 2026-10-23。页面未列明确协议版本。本文记录当前代码能力与上线门槛；本地测试不代表供应商认证、UAT 通过、白名单生效或真钱充值已经开放。

## 当前运行状态

VPay 建单、回调结算及自动恢复均采用显式开关。仓库不会设置这些开关，也不包含商户密码、API Key、Authenticator、回调密钥或查单密钥。现有测试部署保持真实交易关闭；只有部署负责人完成供应商 UAT、来源 IP 白名单、凭据轮换和环境核对后，才可逐项设置服务端秘密并另行验收。

代码接受供应商成功码 JSON 数字 `0` 或精确字符串 `"0"`，拒绝 `"00"`、其他字符串和非零代码。该兼容性不改变资金判断：建单成功仅表示取得付款订单，不能增加会员钱包。

## 订单与会员身份

会员下单时，系统从数据库重新读取当前身份，并要求：

- 账号角色为已批准 customer；
- 存在明确的 `members` 租户记录；
- 账号不是租户老板或员工；
- 会话租户与数据库租户一致。

没有 `members` 记录的账号不会默认落入 `main`。预留订单和最终入账都会在事务中锁定用户及会员归属，再读取一次权威身份。账号停用、职责变化或租户变化会停止入账并建立财务复核记录。

建单使用会员范围内的幂等键和请求指纹。指纹绑定商户、环境、金额、通道、付款人和返回地址；同一幂等键不能换金额或通道。请求已经发出但供应商响应丢失时，订单进入 `unknown`，系统不会自动重发建单，避免创建两张可付款订单。

## 回调、独立查单与原子入账

VPay 通知先由集成网关验签，再通过与建单、查单都不同的机器 Bearer token 转发门户。门户不会只凭浏览器跳转、回调中的 `paid` 或供应商建单结果入账。完整流程为：

1. 校验机器凭据、正文大小、商户、订单、外部订单号、MYR 精确金额及通知状态。
2. 把已验证的语义摘要写入 `portal_vpay_callbacks`。
3. 领取独立 `ORDER_GET` 查询租约。
4. 在数据库事务之外调用固定集成网关查单。
5. 查单结果与商户配置、内外订单号、币种、金额及 paid 状态全部匹配后，进入单一数据库事务。
6. 事务重新锁定会员身份，更新订单、写入唯一双边钱包账本、完成 callback/attempt 并写审计。

回调收件箱只保存订单号、外部订单号、金额、币种、标准化状态、处理状态和时间。它不保存原始 JSON、`sign`、Bearer token、API Key、供应商 remark、银行户口或收款人资料。查询记录同样只保留标准化结果。

重复回调、并发 worker 和重启最多产生一笔钱包入账。每个订单最多有一个进行中的查单；默认查询租约为 120 秒，随机 claim token 同时作为 fencing token。租约过期后新 worker 可以接手，旧 worker 的迟到结果无法更新订单或钱包。回调与独立查单矛盾、入账后出现反向状态、账本缺失或金额不一致时进入人工复核，不会静默删除或自动扣回余额。

迁移 `0011_vpay_reconciliation_runtime.sql` 只建立 VPay 的脱敏回调与查询尝试表及数据库约束，不导入历史订单、不启用通道，也不执行供应商网络请求。

## 可选恢复 worker

恢复扫描默认关闭：

| 变量 | 作用 |
| --- | --- |
| `PORTAL_VPAY_RECOVERY_ENABLED` | 仅字面字符串 `true` 启动恢复扫描；默认关闭 |
| `PORTAL_VPAY_RECOVERY_INTERVAL_MS` | 扫描间隔，允许 60,000–3,600,000 毫秒；无效或缺省时为 120,000 |

恢复只选择已有可信 `trade_no`、未入账、未复核且没有有效查询租约的 VPay 订单。最近完成查询至少冷却 60 秒，防止供应商故障时热循环。每轮最多处理 25 条。`create_outcome=unknown/in_flight` 且没有 `trade_no` 的订单不会被查询或重发，只能等待可信回调或人工核对。

恢复开关不能单独打开资金能力。结算、订单、回调、查询三条服务端凭据、商户、环境和通道配置仍须全部正确；三条门户与网关凭据必须彼此不同，真实厂家 API Key 只存在于集成网关。

## 其他服务端配置

| 变量 | 要求 |
| --- | --- |
| `PORTAL_VPAY_SETTLEMENT_ENABLED` | 仅 `true` 启用门户回调结算 |
| `PORTAL_VPAY_ORDERS_ENABLED` | 仅 `true` 启用会员建单，同时要求结算开关 |
| `PORTAL_VPAY_TRADER_ID` | 已核对的商户编号 |
| `PORTAL_VPAY_ENVIRONMENT` | 显式 `uat` 或 `production` |
| `PORTAL_VPAY_TRADE_CODES` | 厂家已开通通道的 JSON 字符串数组 |
| `PORTAL_VPAY_RETURN_URL` | 与 `PUBLIC_ORIGIN` 同来源的 HTTPS 返回地址 |
| `PORTAL_VPAY_CALLBACK_TOKEN` | 集成网关至门户回调凭据，32–1024 字节 |
| `PORTAL_VPAY_QUERY_TOKEN` | 门户至集成网关配置及查单凭据，32–1024 字节 |
| `PORTAL_VPAY_ORDER_TOKEN` | 门户至集成网关建单凭据，32–1024 字节 |

不要在文档、前端、日志、GitHub、聊天或截图中填写变量值。付款链接可能包含短期会话资料，只能返回给拥有该订单的会员。

## 已验证范围

SQLite 与 PostgreSQL/PGlite 合成测试覆盖：显式会员绑定、幂等预留、回调去重、并发查单租约、过期 worker fencing、已知外部订单恢复、冷却、身份变化、查询矛盾、事务回滚和重复入账防护。测试不调用供应商，也不处理真实资金。

## 生产开放前仍需完成

- 供应商书面确认签名算法、时区、时钟容差、回调重试及纯文本应答规则。
- 确认 `TRADER_ORDER`、`ORDER_GET` 的准确请求/响应字段、状态码、金额限制和到期时间时区。
- 确认 `ORDER_GET` 是否允许或要求额外 `trade_no` 参数。
- 证明 `uat` 使用厂家许可的隔离测试环境；代码标签本身不能证明没有真钱风险。
- 在厂家后台登记真实服务 IP、回调地址及允许来源，并完成端到端 UAT。
- 重新轮换已在截图或聊天出现过的厂家 API Key、商户密码和相关秘密，验证旧值失效。
- 用厂家结算单完成财务对账，演练退款、撤销、网络超时、重复通知及恢复流程。

以上完成并形成验收证据前，VPay 应继续保持关闭。银行收款公告、商户后台可登录、手机号或验证器已绑定，都不能代替接口 UAT 与资金对账。
