# 独立普通白标平台运行版

只包含顾客前台与老板后台。可独立使用平台账号密码，不依赖 ChatGPT 登录，不含任何游戏、博彩、支付、钱包或供应商接口。它与同项目的 Sites 发布目标共用业务 API 和前后台页面，但采用单独的 Node 运行入口及身份适配器。

## 已实现

- 顾客账号注册，老板核实批准后登录；账号暂停会立即撤销登录。
- 平台账号密码登录、退出、8 小时会话过期。密码用随机盐 scrypt 散列；会话及恢复码仅保存散列。
- 注册/开户时提供一次性恢复码；凭恢复码重设密码，轮换恢复码并撤销所有旧会话。没有假称已经发送邮件或短信。
- 顾客公告、个人服务申请、处理进度、回复。
- 老板公告创建/编辑/草稿/发布/撤下，申请管理，状态及回复，操作记录。
- 品牌名称、欢迎语、HTTPS Logo、主题色、品牌创建与切换、按已核实邮箱分配品牌归属。
- 顾客资源及品牌隔离，服务端角色检查、来源校验、登录/注册/找回限速、每日申请限额。
- SQLite 文件保存，启动时顺序应用已记录的业务表迁移；账号和会话表由独立运行入口初始化。
- 账号管理入口 `/accounts` 属于老板后台，只有老板可批准或暂停账号。

## 运行条件

需要 Node.js 24.19 或更高版本、可持久保存数据的磁盘、反向代理 HTTPS。此 Node/SQLite 入口不能直接放到 Cloudflare Pages 或 Workers 运行。Cloudflare 可作为 DNS/代理；应用本身需要支持 Node 与持久磁盘的服务器。

不要上传 `data/`、密码、恢复码、`.env`、生产数据库或访问令牌到公开仓库。不要使用临时磁盘保存生产 SQLite。

## 安装与构建

在项目根目录使用 `package.json` 与 `pnpm-lock.yaml` 安装完整构建依赖（包括开发依赖）。

```bash
pnpm install --frozen-lockfile
pnpm run standalone:build
pnpm run standalone:test
```

构建结果在 `standalone/dist/`。源代码交付包可能已经附带可复现的构建结果；上线前仍应由接手人员从源码重建并验证。

## 首次创建老板账号

先将 `PORTAL_DATABASE` 设置为服务器的持久磁盘文件绝对路径，再创建账号。命令从标准输入读取密码，至少 12 字符、最多 256 字节；不会创建默认密码，也不会覆盖已有老板。

Linux Bash 示例（在受信任的服务器终端运行，替换示例邮箱）：

```bash
export PORTAL_DATABASE=/srv/service-portal/data/portal.sqlite
read -rs -p '老板密码：' portal_password
printf '%s' "$portal_password" | node standalone/admin.mjs create-owner boss owner@example.com
unset portal_password
```

命令将显示一次性老板恢复码。用户自行妥善离线保存；不要贴到聊天或给其他人。正式登录之前无需向本交接人员提供密码。

## 启动

本地自测可用：

```bash
PORTAL_DATABASE=./data/portal.sqlite PUBLIC_ORIGIN=http://127.0.0.1:8080 PORT=8080 node standalone/server.mjs
```

正式服务器环境变量：

| 名称 | 用途 |
|---|---|
| `PORTAL_DATABASE` | 持久磁盘上的 SQLite 文件绝对路径 |
| `PUBLIC_ORIGIN` | 正式 HTTPS 站点源，例如 `https://portal.example.com`；示例不是已绑定域名 |
| `HOST` | 默认 127.0.0.1；按受保护的反向代理/服务器架构配置 |
| `PORT` | 服务监听端口，默认 8080 |

正式 HTTPS 域名须由接手人员配置。服务器拒绝非本机 HTTP 的 PUBLIC_ORIGIN；正式会话 cookie 使用 Secure、HttpOnly、SameSite=Lax。

反向代理需要转发原始请求路径、Cookie 和 Origin。应用不信任客户端伪造的身份头；通过数据库会话确定身份。反向代理后的 IP 限速默认按直接连接 IP（通常为代理地址），因此同一代理的用户共享 IP 限额；上线前由接手人员按可信代理边界规划，不要直接信任任意 X-Forwarded-For。

访问 `/` 为顾客前台，`/admin` 为老板后台，`/accounts` 为老板账号管理，`/signin` 为登录，`/register` 为注册，`/reset` 为恢复码找回密码，`/health` 为进程健康检查。

## 老板使用流程

1. 使用首次创建的老板账号登录。
2. 在“账号管理”核实注册申请人与邮箱归属，再批准。注册邮箱本身未自动验证，批准不能只看页面显示的邮箱。
3. 在“品牌与成员”创建品牌，配置外观，按已核实邮箱分配顾客。未分配的顾客使用默认 main 品牌。
4. 顾客提交服务申请，老板切换到相应品牌处理并回复。

这是一个全局老板管理多个品牌的模型，没有每个品牌各自独立老板或员工门户。不要将它描述成已实现总部/租户老板/员工三级角色。

## 备份与恢复

创建一致性数据库备份（目标必须是尚不存在的文件）：

```bash
node standalone/admin.mjs backup /secure-backups/portal-20261021.sqlite
```

SQLite `VACUUM INTO` 创建快照。备份包含账号、密码散列、会话、恢复码散列和业务资料，应与生产数据库一样保护。

恢复时先停止服务、备份当前数据库和 SQLite WAL/SHM 状态，确认接手人员的恢复方案后替换为所选一致性快照，再启动并核实数据。未经确认不要覆盖现有生产数据。恢复后应撤销全部旧会话并复核账号状态。

## 测试范围

`standalone/test.mjs` 启动真实本地 HTTP 服务和临时磁盘数据库，测试账号注册/审批/登录、密码散列、会话 cookie、前后台权限、申请/回复保存、品牌隔离、恢复码轮换及会话撤销、退出、暂停、会话过期、来源校验、限速、持久数据和静态构建文件。

测试不写入用户生产库，不使用实际客户账号。本地测试不能替代正式域名、TLS、真实手机、多用户并发、备份恢复和真实运行环境验收。

## 仍未包含

正式域名/HTTPS部署、旧站客户数据迁移、邮件或短信找回、OTP、三语切换、附件上传、品牌独立老板及员工角色。外部游戏、支付等由用户另行安排，不属于本平台交付内容。不得将本包称为已完成原 MASTER7 生产站迁移。
